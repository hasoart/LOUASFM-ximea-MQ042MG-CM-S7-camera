# Структура и результаты разбора исходника

## Почему новый рабочий модуль выделен отдельно

В исходном NewTmDAQ_v2 входной ThuliumHub.py сразу импортировал камеры,
сканеры, аналоговые панели и DLL-зависимости. DisplayWindow.py объединял
драйверы, UI, фитирование, таблицы, сохранение и температурные серии в одном
файле около 1600 строк. `core_rub.py` загружал stt_cam.dll через ctypes.windll
при импорте, а `core.py` выбирал x86 toupcam.dll. Встречались абсолютные
Windows-пути, фиксированные размеры кадров и аппаратные коэффициенты другой
камеры. requirements.txt содержал лишь `numpy` и `pil` и не описывал среду.

StatusDisplay.py содержал UI и фоновый UDP-приём, менял элементы интерфейса из
потока и принимал только 1024 байта. Старый адрес UDP 8081 не соответствует
текущему ThuliumBB. Инициализация нескольких камер происходила при создании
панелей. Старые модели и сканеры широко использовали общие изменяемые globals.

Вместо частичного удаления импортов оставлена вся историческая прикладная
часть в `legacy/`; новый запускаемый модуль использует только собственные
пакеты и явно перечисленные зависимости. Это сохраняет материал для будущего
переноса анализаторов без загрузки старых DLL и не переносит неподтверждённую
атомную калибровку на новый сенсор. Исходная папка сохранена отдельно.
Копирование исключало старую `.venv`, кэши и вложенную установленную копию
TensorFlow. Старые runtime-картинки и бинарники не добавлялись в Git.

## Модули

| Путь | Ответственность |
| --- | --- |
| `app.py`, `__main__.py`, корневой `main.py` | Аргументы, журнал, создание QApplication, завершение по сигналам |
| `models.py` | CameraSettings и Frame, проверка значений, описание сырых пикселей |
| `config.py` | JSON-конфиг, значения по умолчанию, атомарная замена и backup |
| `cameras/base.py` | Минимальный Protocol и фабрика драйверов |
| `cameras/basler.py` | Только pypylon/GenICam, поиск, ForceIP, параметры и захват |
| `cameras/simulated.py` | Генерация синтетических изображений; явная имитация внешнего импульса |
| `services/acquisition.py` | Один владеющий камерой поток, очередь команд, одиночный снимок/серия |
| `services/storage.py` | Независимый ограниченный поток записи TIFF/PNG + JSON |
| `services/beaglebone.py` | Стандартная библиотека, UDP-парсер/клиент, снимок последнего контекста |
| `services/analysis.py` | ROI, статистика и средние проекции в единицах пикселей |
| `ui/camera_panel.py` | Поля камеры и диалог ForceIP |
| `ui/image_view.py`, `ui/pulse_view.py` | Представление изображений/профилей и схемы |
| `ui/main_window.py` | Компоновка, команды пользователя, сохранение UI-настроек |
| `scripts/` | Диагностика, загрузка документации, упаковка переносимой копии |

Строки в таблице, начинающиеся с app/models/cameras/services/ui, относятся к
пакету `louasfm_camera/`. Qt нужен оркестратору AcquisitionService для доставки
сигналов, но драйверы, запись, анализ и сетевой протокол независимы от Qt.

## Потоки и владение

```text
Qt main thread ──команды──> camera-owner ──задания──> image-writer
     │                           │                       │
     └──100 ms── latest frame <──┘                       └──TIFF/PNG + JSON
     │
     └──Qt signals <── beaglebone-monitor (UDP)
```

Открытие/настройка/start/read/trigger/stop/close камеры выполняются одним
потоком; UI не вызывает SDK. Чтение ждёт максимум 100 мс за попытку, поэтому
остановка обрабатывается и при молчащем внешнем триггере. pylon запускается с
OneByOne, MaxNumBuffer=16. GrabResult проверяется через IsValid и
GrabSucceeded; пиксели копируются до Release. Упакованные моноформаты
проходят ImageFormatConverter в Mono16 с LSB alignment.

GUI забирает последний кадр из одного слота, а не получает бесконечную очередь
полных изображений через сигналы. Принятый для записи кадр передаётся в
ImageWriter; переполнение восьмиэлементной очереди — явная ошибка с остановкой.
Сохранение в ещё одном потоке не мешает приёму следующего кадра. Приём не
гарантирует отсутствие сетевых/аппаратных потерь; это отдельное измерение.

При завершении окно остаётся открытым с отключёнными органами управления,
пока камера закрывается и очередь записи опустошается. Нет принудительного
kill потока, который мог бы потерять буфер или повредить файл. Отказ записи
доходит до UI и останавливает серию. Отклонённая повторная команда start сама
по себе не прерывает уже идущую запись. Неуспешная конфигурация закрывает
устройство, поскольку предыдущие параметры могли примениться лишь частично.

## Сохранность данных

ImageWriter не масштабирует пиксели. Два файла имеют одно уникальное имя с
UTC, frame_id и UUID. Сначала записываются временные файлы, затем заменяются
конечные имена. Каждая запись flush/fsync выполняется перед переименованием.
Замена двух файлов не является общей транзакцией: при отказе между rename
изображение может оказаться без JSON; ошибка сообщается, а исходный снимок
сохраняется. Файлы с окончанием `.part` не считаются законченными снимками.

Конфиг и backup также пишутся через временный файл и os.replace. Два
одновременно запущенных приложения с одним --config могут перезаписать
настройки друг друга; используйте отдельные пути для независимых сеансов.
Неподдерживаемая версия или повреждённый JSON вызывает ошибку.

## Границы первой версии

В этой версии нет автоматических сканеров, управления DDS/токами, фитов,
расчёта числа атомов, авто-DHCP/persistent IP, обновления прошивки,
многокамерной синхронизации, гарантированной привязки каждого кадра к циклу,
мониторинга всех SDK-событий overtrigger и извлечения chunk-данных. Добавление
этих функций требует явных тестов и аппаратной валидации. Реальная камера и
Windows в этой среде недоступны; SDK-эмулятор не моделирует весь GigE-тракт.
